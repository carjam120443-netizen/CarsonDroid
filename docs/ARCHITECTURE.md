# CarsonDroid architecture

## Boot layers

CarsonDroid separates the development VM path from the experimental PC ISO path.

1. AOSP Android userspace
2. CarsonDroid product/device configuration
3. Android boot image (kernel + ramdisk)
4. PC bootloader/UEFI layer
5. ISO or disk image packaging

The Cuttlefish target is the baseline validation platform. The PC boot path must not assume that a Cuttlefish boot image is directly bootable by GRUB.

## Planned persistent layout

The eventual installer uses an EFI system partition plus Android filesystem partitions and persistent userdata. Dynamic partitions should be generated by AOSP tooling rather than hand-written filesystem images in release builds.

## VM targets

- Cuttlefish: `aosp_cf_x86_64_phone`
- VirtualBox: experimental PC boot path
- QEMU: experimental direct-kernel/image path

## Security modes

Development builds use `userdebug` and may expose ADB. Release builds must use production SELinux policy and must not use permissive debug boot arguments.

## Update architecture

OTA packages are planned around AOSP's update mechanisms. The project should preserve AOSP signing/update semantics rather than inventing an incompatible package format.

## Recovery

Recovery will be a dedicated CarsonDroid recovery environment for maintenance, factory reset, sideload/update operations, and diagnostics. It is intentionally not enabled as a fake boot image until a real recovery implementation is built.
